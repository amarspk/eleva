# CTO ENGINEERING AUDIT — Zayjar Restaurant SaaS Platform

**Audit date:** 2026-08-03 (Asia/Dubai)
**Commit audited:** `0f663ed` (= `origin/main`, verified in sync)
**Auditor mandate:** read the entire repository; trust ONLY source code; ignore implementation reports and PROJECT_STATE claims.
**Method:** static source inspection — route enumeration, schema-to-API coverage mapping, dependency verification, grep-based stub/mock detection, frontend page inventory. No code was modified, no commits created.

> **Audit stance.** PROJECT_STATE.md is a high-quality *backend defect ledger*. Where it makes claims, those claims were largely accurate **within their stated scope**. The critical issue is **scope**: PROJECT_STATE tracks the modules that exist and is nearly silent on whole product surfaces that were specified but never built. This audit measures the codebase against the **product**, not against the ledger.

## 2. CRITICAL FINDINGS (P0 — block production)

### 2.1 AUDIT-001 — No CSS framework exists; entire UI is unstyled
- **What is missing:** Every component uses Tailwind utility classes (`bg-gray-50`, `text-xl font-bold`, `md:grid-cols-2`), but Tailwind is **not a dependency in any app**, there is **no `tailwind.config.*`**, **no `postcss.config.*`**, **no `.css` file anywhere in the repo**, and **no stylesheet import in any `layout.tsx`**.
- **Why required:** The product renders as unstyled HTML. Class attributes are inert strings. This is not a polish issue — the customer-facing QR ordering page, the POS, and the admin panel are all visually non-functional.
- **Difficulty:** Medium (install + configure is small; auditing ~3.5k LOC of markup and building a real design system is the real cost).
- **Dependencies:** Blocks AUDIT-002 (responsiveness), AUDIT-014/015 (dashboards), AUDIT-018 (public site).
- **Note:** PROJECT_STATE §7 SPEC-DRIFT lists "Tailwind/Radix mandated by docs but absent" as a *Low* documentation-drift item. **That severity is wrong** — it is a P0 product defect.

### 2.2 AUDIT-002 — Payments are non-functional and contain a verification bypass
- **What is missing:** The `Payment` model (schema:582) is **never written by any code path** (grep for `payment.create`/`prisma.payment` = 0 hits in `src`). `verifyPayment()` (`wallet.service.ts:258-275`) ignores its inputs and **returns `status:'succeeded', verified:true` unconditionally**. The Tap Payments branch returns a mock charge ID **even when `TAP_PAYMENTS_SECRET_KEY` is set** (`wallet.service.ts:209-223`, comment: *"we mock success for test/dev"*).
- **Why required:** Money cannot be taken, reconciled, refunded, or audited. Worse, any caller can claim a payment succeeded — an order can be marked paid without a real transaction. This is a **financial-integrity vulnerability**, not merely an incomplete feature.
- **Difficulty:** High.
- **Dependencies:** Requires AUDIT-016 (Payment persistence) first; blocks any real revenue.

### 2.3 AUDIT-003 — Mock-user authentication fallback in production login path
- **What is missing:** `auth.service.ts:441-470` — when `DATABASE_URL` is unset, `validateLogin` **fabricates a `RESTAURANT_OWNER` user** with permissions and proceeds. The guard is an env-var check, not a `NODE_ENV !== 'production'` assertion, and it lives in the shipped production bundle.
- **Why required:** A misconfigured or env-stripped deploy converts the login endpoint into an authentication bypass granting owner-level access. Defence-in-depth requires this code to be physically absent from production builds.
- **Difficulty:** Low (delete the branch; fix the tests that rely on it).
- **Dependencies:** None. **Should be fixed immediately.**

### 2.4 AUDIT-004 — No user management: the platform cannot onboard staff
- **What is missing:** No endpoint to create, invite, list, update, deactivate, or delete users; no role-assignment API. The only user ever created is the owner, inside the onboarding transaction.
- **Why required:** A restaurant cannot add a cashier or kitchen user. Both staff apps (Cashier, KDS) therefore have **no reachable users** in a real deployment. The product is unusable end-to-end regardless of backend quality.
- **Difficulty:** Medium.
- **Dependencies:** Needs AUDIT-005 (password reset / invite email).

### 2.5 AUDIT-005 — No password reset and no email verification
- **What is missing:** Zero matches for `forgot-password`, `reset-password`, `verifyEmail` in `apps/api/src`. A `password-reset` **email template exists** (`email.service.ts:52`) with no flow behind it.
- **Why required:** Any user who forgets a password is permanently locked out; unverified emails permit account squatting. Baseline SaaS requirement.
- **Difficulty:** Medium.
- **Dependencies:** EmailService (exists).

## 3. HIGH-SEVERITY FINDINGS (P1)

### AUDIT-006 — Menu management is create-only (no update/delete)
Products, categories, sizes, and addons can be **created and listed but never edited or removed** (`menu.controller.ts` has 7 POST/GET routes, zero PUT/PATCH/DELETE). A typo in a price is permanent; a discontinued dish cannot be removed. **Difficulty:** Medium. **Dependencies:** none (schema supports it; `Product.isAvailable` exists but is unreachable).

### AUDIT-007 — Branch and table management is create-only
`POST/GET /branches`, `POST/GET /tables` only. No rename, no deactivate, no delete, no QR regeneration. **Difficulty:** Low–Medium. **Dependencies:** none.

### AUDIT-008 — No restaurant module
`Restaurant` (schema:268) is created once at onboarding and never surfaced. Multi-restaurant tenants (an explicit DOC-001 §1.9 concept) are unmanageable. **Difficulty:** Medium. **Dependencies:** AUDIT-014.

### AUDIT-009 — Discounts have no management API
The engine is real and well-tested, but `Discount` rows can only appear via seed. Merchants cannot create a promotion. **Difficulty:** Low (engine done; CRUD + guards only). **Dependencies:** AUDIT-014 for UI.

### AUDIT-010 — Invoices are generated but unreachable
Real PDFs are rendered and stored, but there is **no invoice controller** — no list, no download-by-id, no email-resend. Output is write-only. **Difficulty:** Low. **Dependencies:** none.

### AUDIT-011 — No API documentation
No `@nestjs/swagger`, no `DocumentBuilder`, no OpenAPI spec. DOC-003 covers 23 endpoints; 44 exist, so **~21 routes are entirely undocumented**, including all public guest routes. **Difficulty:** Low–Medium. **Dependencies:** none.

### AUDIT-012 — E2E tests are fully mocked and excluded from CI
`tests/e2e/*` intercept every API call via `fixtures/api-mocks.ts` and assert against `mock-data.ts`; `ci.yml` never invokes Playwright. These tests **cannot detect a backend regression** and provide false assurance. **Difficulty:** Medium. **Dependencies:** needs seeded environment in CI.

### AUDIT-013 — Domain management is a field, not a feature
`customDomain` is settable and plan-gated, and middleware resolves it — but there is **no ownership verification (DNS TXT), no CNAME validation, no TLS/ACME provisioning, no status tracking**. A tenant can claim `mcdonalds.com`. **Difficulty:** High. **Dependencies:** ingress/cert-manager integration.

## 4. MEDIUM-SEVERITY FINDINGS (P2)

### AUDIT-014 — Restaurant Dashboard is a read-only demo panel
`AdminPanel.tsx` (298 LOC) runs 4 read queries and renders lists. **No mutations** (`useMutation` = 0 hits). Defaults to hardcoded `'tenant-uuid-1111'` / `'branch-uuid-1234'`. No analytics, no reporting, no settings, no staff management. **Difficulty:** High. **Dependencies:** AUDIT-001, 004, 006, 007, 009.

### AUDIT-015 — Platform Dashboard has no UI and one endpoint
Only `GET /admin/tenants/metrics`. No tenant listing, suspension, plan override, impersonation, or audit review — and **no platform-owner frontend exists**. The business cannot operate its own SaaS. **Difficulty:** High. **Dependencies:** AUDIT-001.

### AUDIT-016 — Payment records are never persisted
Distinct from AUDIT-002: even the Stripe path writes no `Payment` row, so there is no reconciliation ledger, no refund trail, no revenue reporting. **Difficulty:** Medium. **Dependencies:** prerequisite for AUDIT-002.

### AUDIT-017 — Subscription lifecycle is incomplete
Checkout + webhook sync exist. **No cancel, upgrade, downgrade, reactivate, proration, or billing-portal** endpoint. Merchants cannot change plans; support must use the Stripe console. Returns a **mock checkout URL** when `STRIPE_SECRET_KEY` is unset (`billing.service.ts:63-71`). **Difficulty:** Medium. **Dependencies:** none.

### AUDIT-018 — No public restaurant website
`apps/qr-menu` requires a table token (`?t=`) and returns an error view without one. There is no browsable restaurant page, no menu-without-QR, no hours/location/contact, no SEO metadata, no Open Graph. Guests can only order at a physical table. **Difficulty:** High. **Dependencies:** AUDIT-001, 013.

### AUDIT-019 — No mobile viewport meta; responsiveness unverifiable
No `viewport` export or `<meta name="viewport">` in any `layout.tsx`; only two responsive breakpoints (`md:grid-cols-`, `lg:grid-cols-`) exist across the whole frontend. Since Tailwind is absent (AUDIT-001), even those are inert. **The QR guest flow is inherently mobile-first** — this is a primary-path defect. **Difficulty:** Medium. **Dependencies:** AUDIT-001.

### AUDIT-020 — Helmet absent (no application-level security headers)
`helmet` is not a dependency and `main.ts` never registers it. nginx.conf sets CSP/HSTS/X-Frame-Options, but that only protects traffic through that specific ingress — direct pod access, port-forwards, and non-nginx routes are unprotected. Defence-in-depth requires both. **Difficulty:** Low. **Dependencies:** none.

### AUDIT-021 — SMS Unifonic path mocked even when configured
`sms.service.ts:167-168`: *"Mock Unifonic API call (real implementation would use axios POST)"*. Twilio is real; the Middle-East router — the primary region per DOC-008 §7.3 — is not. **Difficulty:** Low. **Dependencies:** none.

### AUDIT-022 — No notification preferences or in-app inbox API
`Notification` rows are persisted (FCM mirror) but there is **no controller** to list, mark-read, or configure per-user channel preferences. **Difficulty:** Medium. **Dependencies:** none.

### AUDIT-023 — Monitoring lacks metrics endpoint and alerting
Datadog APM and `/health` exist; there is no `/ready` vs `/live` split, no Prometheus `/metrics`, no SLO or alert definitions despite HPA scaling 2–10 pods. **Difficulty:** Medium. **Dependencies:** none.

### AUDIT-024 — `packages/db` has zero tests
0 spec files for the tenant-isolation repository layer — the component that enforces the platform's core multi-tenant security boundary. Its correctness is only tested indirectly. **Difficulty:** Medium. **Dependencies:** none.

### AUDIT-025 — M4 partitioning migration remains non-shippable
`20260726000001_orders_partitioning_by_year` fails on apply (`42703`), verified live during this audit's predecessor session. It is excluded from the working chain, so `prisma migrate deploy` on a pristine environment **cannot apply the full committed migration directory** without operator intervention. **Difficulty:** High (architecture RFC — CTO decision, already recorded as R2). **Dependencies:** CTO decision.
